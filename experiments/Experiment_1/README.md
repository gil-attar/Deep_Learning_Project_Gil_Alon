# Experiment 1: Freeze-Depth Fine-Tuning of Pretrained Detectors

## Research Question
**How does detection performance depend on the fine-tuning depth (trainable capacity) when adapting pretrained detectors to a small ingredient dataset, and does this dependence differ between CNNs and Transformers?**

## Hypothesis
Based on the course-driven transfer learning perspective:
1. **Intermediate fine-tuning depths** (partial unfreezing) may provide a favorable trade-off between adaptation capacity and overfitting risk in small-data regimes.
2. Due to architectural differences, **CNN-based detectors** are expected to benefit earlier from shallow-to-intermediate unfreezing (reusing hierarchical features effectively), while **Transformer-based detectors** may require **deeper adaptation** to adjust learned global attention patterns.

## Method

### Freeze Regimes (4 per model)
We decompose each detector into the standard components:
- **Backbone**: feature extraction
- **Neck**: multi-scale feature aggregation/fusion
- **Head**: bounding box + class predictions

Freeze-depth configurations progressively increase the number of trainable parameters:

| Regime | Trainable Components | Description |
|--------|----------------------|-------------|
| F0     | Head only            | Minimal adaptation (fixed backbone+neck feature extractor) |
| F1     | Neck + Head          | Adapts feature fusion + output layers |
| F2     | Late Backbone + Neck + Head | Partial backbone adaptation (higher-level semantics) |
| F3     | Full model           | End-to-end fine-tuning |

> Exact module boundaries and the measured trainable parameter counts are recorded per run (see `run_manifest.json`) and documented under `freezing/`.

### Models
- **YOLOv8m** (CNN-based detector)
- **RT-DETR-L** (Transformer-based detector)

### Evaluation
All configurations are evaluated with the project’s unified evaluation protocol:
- Threshold selection uses **validation**
- Final reporting uses the held-out **test** set
- Primary metrics: **mAP@0.5** and **F1** (with IoU-based matching, IoU ≥ 0.5)
- Additional diagnostic plots are generated by the custom evaluation pipeline (threshold sweep, per-class behavior, confusion matrix, counting MAE)

## Implementation Details

### Colab-First Orchestration (Main Entry Point)
Experiment 1 is designed to be executed primarily via the **Google Colab notebook**:

- **Notebook:** `E1_run_evaluate.ipynb`
- The notebook:
  1. Mounts **Google Drive** for persistent storage of all outputs
  2. Downloads the dataset (Roboflow) and pretrained weights into the Colab runtime
  3. Links the repo’s `experiments/Experiment_1/runs/` directory to a Drive-backed folder
  4. Runs `run_experiment1.sh`, which invokes `runOneTest.py` **8 times** (2 models × 4 freeze regimes)
  5. Aggregates results and saves combined plots back to Drive

This path standardizes environment setup, storage persistence, and end-to-end reproducibility.

### Running sequence

1. Open `E1_run_evaluate.ipynb` in Google Colab
2. Configure parameters in the config cell:
   - `EPOCHS = 50` for the full sweep
   - `DRY_RUN = True` to execute a fast sanity-check (smoke test) without committing to a full run  
     - Set `DRY_RUN = False` for the real experiment
   - `RUN_ID = ""`
     - Leave empty / generate a new ID for a fresh run
     - Set to an existing `E1_...` ID to resume after a disconnect
3. Run all cells — approve the Google Drive mount when prompted, and ensure the Roboflow/data API key is set correctly (as specified in the general `README.md`).

### Resume After Disconnect
1. Check `LATEST_E1_RUN_ID.txt` on your Google Drive
2. Set `RUN_ID = "E1_..."` in the notebook config cell
3. Re-run — completed runs (model × freeze regime) are automatically skipped

## Key Results

### Freeze-Depth Matters, but Differently per Architecture

**Key Findings:**
1. **Monotonic improvement with unfreezing:** For both YOLOv8m and RT-DETR-L, test-set detection performance increases as progressively more layers are unfrozen (F0 → F3).
2. **CNN adapts early:** **YOLOv8m** shows its largest relative gains already at shallow-to-intermediate fine-tuning depths (F0→F1→F2), indicating that limited adaptation of higher-level components is sufficient to effectively reuse pretrained convolutional features.
3. **Transformer needs deep adaptation:** **RT-DETR-L** exhibits its most substantial improvement only when the **full network is unfrozen** (F3), suggesting that meaningful transfer requires deeper adaptation of learned attention representations to the target domain.
4. **“More parameters” is not the whole story:** Performance improves with increasing trainable capacity, but not uniformly across models. Because each freeze regime unfreezes *different architectural components* (not a fixed parameter count), **which layers are unfrozen matters more than the absolute number of parameters.**

## Conclusion
Freeze-depth matters, but its effect differs by architecture. CNNs tend to obtain most performance gains under shallow-to-intermediate fine-tuning (head/neck and limited upper backbone), whereas a transformer is likely to require deep or full unfreezing to realize substantial improvements. To improve transformer fine-tuning efficiency, a progressive unfreezing schedule can be evaluated: first train task-facing layers to align predictions to the target dataset, then unfreeze additional deeper layers so attention representations can adapt as training signals become cleaner. A short learning-rate warmup during the transition stabilizes updates and reduces the risk of abrupt, destabilizing parameter changes.
